# Architecture Review: met-timeseries

## What you're doing well

The **conceptual decomposition is genuinely good** — arguably the hardest part, and you have it right:

- **Layering**: `sources/` (acquisition) → `derivations/` (physics) → `disaggregation.py` (temporal) → `weights.py` (spatial) is exactly the right factoring for your ensemble-forcing goal.
- **The conservation-typed disaggregation framework** is the best abstraction in the codebase. Classifying methods by what they conserve (`sum` / `mean_additive` / `mean_multiplicative`) rather than by variable name, with frequency inference instead of hardcoded "1D"→"1h", is precisely the foundation "arbitrary timestep" needs. The dispatch registries make methods swappable — that *is* your future sensitivity-analysis knob.
- **Derivations as a method library**: pure xarray functions, unit-suffixed names, a `constants.py`, and *multiple* methods per quantity (4 cloud-cover estimators, several clearsky models, several PET formulations including the legacy-faithful `penman_knb`). This is exactly what "multiple forcing versions for HSPF" requires.
- **Domain care**: the PRISM 12Z–12Z window shift in `_shift_time_coord`, equal-area projection for weights, half-cell padding on clips, ascending/descending latitude handling, and the hybrid PRISM-mass × NLDAS-pattern precipitation logic are all subtle things people commonly get wrong.
- **Right cloud instincts**: `earthaccess` (supports S3 direct access), cache-then-clip against a canonical `CACHE_BOUNDS`, WKB-keyed LRU weight caching, chunk-aligned batch appends to Zarr, and the `audit_netcdf_cache` instinct in `_zarr.py`.

## The core structural problem: no working spine

The package is currently **several refactor generations coexisting, none of which is complete**. This is the biggest architectural liability — worse than any individual design flaw:

- `pipeline.py` imports `met_timeseries.config`, `.ledger`, and `.io` — **none exist**. It calls `derive_variables`, `aggregate_over_polygon`, and `fetch_nldas_grid` — **none exist**. It calls `fetch_prism(bounds, start=…, end=…)` — the real signature is now `fetch_prism(date, cache_dir, …)`. The orchestration layer is dead code.
- `pyproject.toml` declares a `met_timeseries.cli:main` entry point — no `cli` module exists.
- The **entire test suite tests a previous generation**: `met_timeseries.aggregation` (renamed to `weights`), `met_timeseries.ledger` (deleted), `disaggregate_temperature_pattern`, `_normalise_weights`, `prism._fetch_single_day` — the suite would fail at import. You have ~130KB of tests providing zero protection, which is why bugs like the ones below survive.
- `quickstart.py` imports the deleted `config` module; the README describes the old Parquet pipeline.
- `MetTool_Historic.py` (91KB wxPython GUI importing `wx`, `osgeo`, `wdmtoolbox` at module level) lives *inside* the installable package. It's reference material — it belongs in `references/`, not `src/`.
- `_zarr.py` is a scratch script masquerading as a module: it executes `open_mfdataset` at import time against hardcoded `C:\Users\mfratki\...` paths, duplicates blocks, and calls a commented-out `main()`. Also a real bug: `netcdf_to_zarr` ignores its `netcdf_dir` argument and uses the module-level `files` global.

The pattern underneath: **experiments are kept by copying rather than by branching**. `download` vs `download_bulk`, `disaggregate_precipitation_hybrid` vs `_disaggregate_precipitation_hybrid`, `_weights_normalise` vs `_weights_normalise_respec`, three copies of `clip_dataset` (in `utils.py`, `nldas.py`, `prism.py`). Every duplicate is a place where a bug fix lands once and misses the other copy. Use git branches for experiments and delete the losers.

## Specific brittle components and bugs

**Correctness landmines (these will silently corrupt data):**

1. **NLDAS time-axis mislabeling** — `download` skips failed granules with a warning, then if the decoded time isn't datetime64, **reconstructs a contiguous hourly axis from the start date**. One failed granule ⇒ every subsequent hour is silently shifted. This is the worst kind of bug for a forcing dataset: it validates, runs, and produces plausible-but-wrong hydrology.
2. **Silent zero-weight polygons** — `build_weightmap` `continue`s when coverage < 99% (your own TODO flags this), leaving that polygon's weights all-zero ⇒ downstream timeseries of all zeros with no error.
3. **Unrenormalized validity masking** — `weights_ds * valid_mask` at the end of `build_weightmap` zeroes weights over nodata cells but never renormalizes, so weights no longer sum to 1 ⇒ **biased-low areal means** for any metzone touching PRISM edges/nodata. It also assumes a `time` dim exists in what's documented as a generic engine.
4. **Broken call chain in the aggregation layer** — `get_weights` passes `dataset=` to `build_weightmap(datarray=…)` (TypeError), and `weighted_mean_timeseries` extracts `["weights"]` and then subscripts it *again* (KeyError). These two functions have plainly never been executed — direct evidence of the dead test suite.
5. **Doc/code drift in PRISM caching** — the comment says "clip to CACHE_BOUNDS" before caching, but `fetch_prism` caches the **full CONUS** raster (at 800m, that's enormous per day-variable) and clips only on read.
6. **Unseeded stochastic disaggregation** — `_molnar_burlando_split` creates a fresh unseeded `default_rng()` per invocation. For a sensitivity study, irreproducible forcings are disqualifying. Seeds must be a first-class, recorded parameter.
7. **Dimensional-contract confusion** — `_weights_diurnal` multiplies a template by a raw 24-hour numpy vector — this only broadcasts correctly for 1-D (time-only) arrays, while `_weights_trapezoidal` *requires* a `lat` coordinate. The "xarray-native framework" silently assumes 1-D in some paths and gridded in others. Decide and validate the contract (e.g., "disaggregation operates on areal-mean series" — see below).

**Design smells:**

- **The one abstraction you defined isn't honored.** `FetchFunction` Protocol in `base.py` documents `(bounds, start, end)`; every real fetcher is now `(date, cache_dir, …)`, and nothing references the Protocol. Update it to match reality (per-date fetch + cache dir is a fine contract) and type-annotate the fetchers against it.
- **No canonical variable schema.** NLDAS yields `Tair` in K; PRISM `tmax` in °C; NDAWN `'Avg Air Temp'` in °F; derivations variously expect °C or K; nothing validates. For "multiple sources feeding the same models," the single most valuable architectural addition is a **normalization boundary**: every source adapter emits CF-ish canonical names + units + UTC time + CRS attrs, and everything downstream trusts only that schema. Right now unit errors are undetectable by construction.
- **`utils.py` is a grab-bag** — memory profiling, a third `clip_dataset`, and `hdf5WDM` (a WDM/HSPF reader!). That WDM class is the seed of your **export layer** — the thing that will eventually write forcings into HSPF — and deserves promotion to its own module, not burial in utils.
- **`base.py` imports matplotlib at module level** — every source import drags in a GUI-adjacent plotting stack. In a cloud container/Lambda this is dead weight and a frequent breakage source. Plotting belongs in a `viz` module.
- **Dependency manifest is fiction.** The code imports `pvlib`, `pyet`, `scipy`, `zarr`, `dask`, `psutil`, `h5py`, `netCDF4`, `pyproj`, `matplotlib` — none declared in `pyproject.toml`; `environment.yml` covers only some and diverges from pyproject. `pip install .` produces a package that can't import most of itself. For cloud work this matters doubly: your environment must be reconstructible in a container from the manifest alone.
- **Hardcoded region and paths**: Minnesota `CACHE_BOUNDS` baked into the "generic" base; personal Windows paths in `_zarr.py`. Both belong in configuration (which is exactly the module that got deleted).

## Why your vectorized xarray isn't faster than a for-loop

Your suspicion is correct, and the reasons are specific and fixable. The code *looks* vectorized but the hot paths are not:

1. **The pvlib loops are the dominant cost.** `clearsky_radiation_ineichen`, `extra_radiation_pvlib`, and `daytime_mask_solar_elevation` each run a Python loop over every grid cell (~3,800 cells for your MN bounds at NLDAS resolution), computing full solar-position series per cell. `cloud_cover_davis` calls *two* of these. This alone is minutes per month, per variable.
2. **`apply_ufunc(vectorize=True)` is a Python for-loop.** `disaggregate_precipitation_stochastic` loops per cell in Python, constructing pandas Series and fitting a cascade per cell. `vectorize=True` is a convenience wrapper around `np.vectorize` — it provides zero speedup over your old loop; it just hides it.
3. **The one truly vectorizable op is done the slow way.** `_weight_dataset` computes `(dataset * weights).sum(dim=[lat, lon])`. With a `(polygon, lat, lon)` weight cube against `(time, lat, lon)` data, xarray broadcasting **materializes the full `(polygon, time, lat, lon)` intermediate** (hundreds of MB to GB per variable-month) before reducing. This is a tensor contraction and should be expressed as one (`xr.dot`/einsum) — typically a 10–100× difference, and it's likely the single biggest reason "vectorized" feels no faster than looping over 30 metzones.
4. **Work ordering: you compute expensive fields on the full grid, then discard everything but a weighted mean.** Your end product is a per-metzone series. For solar geometry especially (deterministic, smooth in space), computing at the metzone centroid after aggregation is ~3,800× less work than per-cell-then-average. More broadly: **aggregate-then-derive vs derive-then-aggregate is a scientific choice for nonlinear derivations (PET, humidity), but for you it's also the dominant performance lever.** Make it an explicit, per-variable pipeline decision rather than an accident of code structure — it's even a legitimate axis of your sensitivity study.
5. **Stochastic disaggregation per cell is both wasted and scientifically wrong for your product.** Independent per-cell cascades destroy the spatial correlation of rainfall; when you then average cells to a metzone, the independent noise partially cancels and you get systematically over-smoothed hourly hyetographs — bad for HSPF runoff peaks. Disaggregate the **areal-mean series** (post-aggregation) instead: cheaper by orders of magnitude *and* more defensible. This also resolves the 1-D/3-D contract confusion in the disaggregation framework — declare it a 1-D-series framework.
6. **I/O dominates everything anyway.** Thousands of per-day NetCDFs (one time-step per file for PRISM), `complevel=9` compression (very slow to write for marginal size gain over 4–5), `open_mfdataset` metadata crawls. Until reads come from the consolidated Zarr store, algorithmic tuning is rearranging deck chairs.

Recommendation: before touching anything, **profile one month end-to-end** (`pyinstrument` or `cProfile`+snakeviz). I'd bet the ranking is pvlib loops > broadcast-multiply aggregation > NetCDF I/O > everything else. Also: don't reach for dask reflexively — your clipped MN domain fits comfortably in RAM; the wins here are algorithmic (contraction, centroid solar, aggregate-first, store consolidation), not parallelism.

## Cloud-friendliness assessment

Your direction (consolidate the NetCDF cache into Zarr) is right. What's missing for genuine local/cloud interoperability:

1. **Paths are your lock-in.** Everything is `pathlib.Path`, `Path.glob`, Windows separators. The single highest-leverage change for interoperability: treat **fsspec-style URI strings as the only path currency**. `xarray`, `zarr`, and `geopandas` all accept `s3://bucket/prefix` + `storage_options` through fsspec. Done consistently, "local vs cloud" stops being an architecture question and becomes a config value. `Path.glob`-based cache discovery (`get_filepaths`) must become store-native listing or, better, manifest-driven.
2. **Make the store the center of the architecture.** Right now the per-day NetCDF cache *is* the de-facto datastore, with hand-rolled merge-on-missing-variable logic in both `fetch_nldas` and `fetch_prism` (duplicated, fragile). Invert it: an **ingest job** (the productionized `_zarr.py`) writes one canonical, chunk-aligned, consolidated Zarr per source; *everything* downstream reads only the store. Per-day NetCDFs become a transient ingest detail. Your batch-append pattern (batches as multiples of chunk size) is already correct; add the missing pieces: time-monotonicity/gap validation before each append (wire in your own `audit_netcdf_cache`), and a final metadata consolidation.
3. **Idempotency needs a ledger — and you deleted it.** The old `ledger` concept (tracked per-month completion) was the right idea for resumable, idempotent backfills, which is *the* core pattern for cloud batch jobs. Reinstate it as a small manifest keyed by (source, date, variables), stored beside the store itself.
4. **Auth and interactivity in library code**: `earthaccess.login()` is called inside `download()` — interactive prompts are fine on your laptop and fatal in a batch container. Auth should be resolved once at the entry point, injectable, environment-variable driven.
5. **Chunking**: `(time=2160, lat=-1, lon=-1)` full-spatial chunks are a good fit for your access pattern (extract long timeseries over small polygons in a MN-sized domain). One consideration for object storage: many small time-chunks of the *whole* history per read is fine, but revisit chunk size targeting ~5–100MB compressed per object.
6. **Alternative worth knowing**: for NLDAS-2, kerchunk/VirtualiZarr can present NASA's existing files as a virtual Zarr without duplicating bytes. For your clipped-region use case, materializing your own regional Zarr is simpler and I'd stick with it — but it's the standard escape hatch when a future source is too big to copy.

## Alignment with your stated goals

**Arbitrary timestep**: the conservation framework is the right chassis, but hourly is still hardcoded at the leaves — `_weights_diurnal` (24-element list, `"1H"`), `_weights_static`, `_cascade_to_hourly`, and `disaggregate_pevt`. To get there: make `target_freq` a first-class argument of `disaggregate()`; express diurnal patterns as continuous functions of fractional day (evaluable at any Δt) rather than 24-element lists; and note that the multiplicative cascades are **inherently dyadic** (your 45-min→15-min→hourly trick) — arbitrary Δt from cascades requires a conservative resampling stage or accepting dyadic timesteps for the stochastic path. Also, timezone discipline (NLDAS UTC, PRISM 12Z-shifted, NDAWN CST, HSPF wanting local standard time) is currently implicit and naive everywhere; it gets more dangerous as Δt shrinks.
